# Dashboard visual consistency and card sizing

## Direction

Improve the existing Black Rose design rather than replace it. Overview, My Games and Teams use the shared `MemberHeroBanner`, existing display/tech typography, dark panels, clipped cards, game accents and established button treatments. The experimental compact dashboard header and sidebar layout were rejected; the unused `DashboardPageHeader` component was removed.

Overview keeps its original stat strip, three-card row (profile completion, identities and registration), and two-card row (matches and social links). The subtle three-identity preview and `N more` / `Show less` behavior are preserved.

## Scoped refinements

- Overview grid cards stretch to equal height **within each desktop row**. Expanding identities recalculates the row naturally; no fixed pixel height, cropping or content removal is used. Mobile Overview cards stack and grow with their own content.
- Joined-team cards share equal-height grid rows. Their body flexes to fill available space, including when only some teams have a tournament footer. Long names remain readable and can wrap on mobile.
- Stat values, game labels and identities wrap rather than force horizontal overflow. Registration actions stack inside the narrower Overview card instead of squeezing the event information.
- Team and invitation cards retain their original branding, with smaller spacing/tags only at narrow widths and 44px action targets.
- Captains see `Manage team`; members see `View team`, using the same existing team route and permissions. Championship/tournament links remain available.
- Invitation/action failures leave existing teams and invitations visible with retry. Initial read failures are not presented as an empty roster. Existing pending disables, navigation, read markers, cache invalidation and create intent remain intact.
- The original social panel keeps linked, private and missing states; a genuinely empty social list receives a brief hint rather than a blank card.

## Deployment boundary

This is application presentation work. No new migration, environment change, Discord bot/Worker change, database data replacement, commit, push or production deployment is part of it. Keep the previously documented trusted-session and game-membership prerequisites for a separately authorized release. Application rollback should preserve all existing member, team, registration and membership data.
